## Digest equality — what was verified, and what was not

`R-EXACT-ARTIFACT` requires the deployed digest to equal the verified
digest. The build verified on 30 August under `M-0001` had digest
`sha256:6a4a9307…7527` (its receipt). The served digest is
`sha256:a8b72039…cd7a`. **They differ, and the difference is the build
date:** the page embeds the day it was built — the one value on it with no
record behind it, as the `M-0001` receipt says — and Vercel built it on
31 August rather than 30.

**Reproduction.** A clean worktree at `9792eb5`, `pnpm install && pnpm
proof`, run by the agent on 8 September 2026, produced
`sha256:74a9b49d…0682` — a third digest, because it embeds 8 September.
With the *built* row normalised in both files, **the local build and the
served page are byte-identical.** So the served artifact is the verified
source, built on a different day. That is reproduction modulo one known,
declared field — not digest equality.

**Class:** `CHECKED`. A person ran the comparison and this receipt records
it; the kernel does not attest running artifacts, and the attestation half
of `R-EXACT-ARTIFACT` remains `DECLARED`, exactly as the constitution says.

**What would make it `ENFORCED`:** an injectable build date, so that a
release records a digest the deploy reproduces byte for byte. That is a
change to `apps/proof/src`, denied under `M-0004` and under
`M-0001-RELEASE` alike, and is proposed for a later mandate.

**One thing recorded and not explained:** the response's `last-modified`
header reads 8 September 2026 14:55 GMT, eight minutes before the fetch,
while the page says it was built on 31 August. The header is the CDN's;
the date in the page is the build's. Whether Vercel redeployed the same
artifact on 8 September is a fact in the Vercel deployment log, which the
agent cannot read. Confirmer: founder, `[CONFIRM]`.
