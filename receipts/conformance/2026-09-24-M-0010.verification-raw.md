DEFECTS

1. MEDIUM. Test: "DEFECT: an invite used while a block commits leaves the friendship standing, and unblocking restores friends-only access without a new acceptance"
Cause: src/core/invites.ts:567 checks for a block, then :588 inserts the friendship. src/core/connections.ts:467-529, `block()`, takes no lock on the pair.
If a block commits between that check and the insert, the friendship row exists alongside the block. The test forces this order with a table lock. It finds 1 friendship row after the block. After unblocking, the guest can see the inviter's friends-only post with no new request or acceptance. Doing the two operations one after the other, in either order, leaves no friendship. Friend-request acceptance already handles this race correctly (`acceptWithin`); invite use does not.
Smallest fix: at the start of `block()`, and inside the transactions of `useInviteAsExisting`, `follow`, `toggleLike` and `sendFriendRequest`, take `pg_advisory_xact_lock` on the unordered pair (least:greatest). Then check `isBlocked` again after getting the lock.

2. LOW. Test: "DEFECT: a follow made while a block commits survives the block, and unblocking restores the follower's reach"
Cause: src/core/connections.ts:408 checks visibility, then :420-434 inserts the follow. `block()` takes no lock.
After the block there is still 1 follow row. After unblocking, the follower sees followers posts again, although SPEC §6 says a block deletes follows.
Smallest fix: the same pair lock as in 1.

3. LOW. Test: "DEFECT: a follow made while accepts_followers is switched off survives, and reaches followers posts again when it is switched back on"
Cause: src/core/connections.ts:417 reads `acceptsFollowers` outside the insert's transaction. src/core/accounts.ts:236 deletes follows without serialising against a follow in flight.
Smallest fix: in `follow()`, lock the followee's account row (`select … for share`) inside the transaction, check `accepts_followers` again, then insert.

4. LOW. Test: "DEFECT: a like made while a block commits survives the block, and the author sees the blocked person among the likers after unblocking"
Cause: src/core/posts.ts:525 checks `canSeePost` outside the transaction that starts at :527.
Smallest fix: the pair lock from 1, then check `canSeePost` again inside the transaction.

5. LOW. Test: "DEFECT: a friend request sent while a block commits survives as pending, and reappears to the blocker after unblocking"
Cause: src/core/connections.ts:259 checks visibility, then :278-292 inserts the request.
After unblocking, the blocker sees an incoming request from the person they blocked. SPEC §6 says a block cancels pending requests both ways.
Smallest fix: the pair lock from 1.

6. LOW. Test: "DEFECT: postPage (exported from core/posts) hands a stranger a friends-only post when its caller forgets the predicate"
Cause: src/core/posts.ts:255, `postPage`, is exported and only a comment asks the caller to pass the visibility rule.
No current caller misuses it. But the M-0010 acceptance test says "through any page or core function", and `postPage(db, strangerId, eq(posts.id, x))` returns the body of a friends-only post.
Smallest fix: inside `postPage`, use `and(visiblePostPredicate(viewerId), where)`, or stop exporting it.

7. MEDIUM. Test: "DEFECT: /people/invites (listInvites) names an invitee who has since blocked you — even their new handle — while a deleted invitee shows nothing"
Cause: src/core/invites.ts:210 hides a suspended invitee but not one who blocked you.
The inviter sees the blocker's current handle, even after it changes, and it links to a profile that is not found. A deleted invitee shows nothing. So the list tells "blocked you" apart from "deleted", against SPEC §2 rule 3, and leaks the new handle.
Smallest fix: return `usedByHandle` only when `canSeeAccount(inviter, usedBy)` holds, which covers active and no block either way.

8. LOW. Test: "DEFECT: the export names a suspended invitee (used_by_handle) that /people/invites hides"
Cause: src/core/export.ts:292, with the join at :237-242, has no suspension or block filter. This is the rule the code applies at invites.ts:210.
The export gets around the page's own hiding rule.
Smallest fix: the same condition as 7 when filling `used_by_handle`.

9. MEDIUM. Test: "DEFECT: /settings/blocked (listMuted) keeps showing someone who blocked you, with their new name, while a deleted account drops out"
Cause: src/core/connections.ts:724-734, `listMuted`, has no block or suspension filter.
Same leak as 7: it shows the blocker's current name and handle, and whether they blocked you rather than deleted their account.
Smallest fix: filter `listMuted` by `canSeeAccount`. The mute row can stay; it has no effect while the block exists.

10. LOW. Test: "DEFECT: mute() and block() by id answer differently for a person who blocked you (ok) and a deleted account (NOT_FOUND)"
Cause: src/core/connections.ts:557 in `mute` and :475 in `block` use `exists()`.
I confirmed this over HTTP: `muteAction` on someone who blocked you returns `{ok:true}`; on a missing id it returns "That person isn't available." `block()`'s own comment says refusing would tell you they had blocked you, and refusing the deleted case tells you the same thing by contrast.
Smallest fix: for a missing account, return success without writing anything, instead of NOT_FOUND.

11. LOW. Test: "DEFECT: the unread badge (countUnread) counts notifications that /notifications (listNotifications) hides, so it signals activity by a suspended account"
Cause: src/core/notifications.ts:66-74 has no filter on who caused the notification. inbox.ts:107 does filter.
The badge shows 1 while the list is empty.
Smallest fix: add `or(isNull(actorId), personShownTo(accountId, actorId))` to `countUnread`.

12. LOW (spec tension). Test: "DEFECT (spec tension): changing your username tells you a handle is held by someone who blocked you, or by a suspended account, though their profile is not found"
Cause: src/core/accounts.ts:183 answers "That username is taken" (CONFLICT), with no rate limit.
Unique handles make this hard to close completely, so it needs your decision rather than a builder fix. Smallest step: rate-limit handle changes, and either accept and document the remaining oracle on /rules or amend SPEC §2 rule 3.

3. MEDIUM (depends on where it is deployed) — the per-IP limits trust x-forwarded-for, which the client can write, and nothing limits a single invite.
   Tests: "DEFECT: the per-IP sign-in limit is keyed on x-forwarded-for, which the client writes" and "DEFECT: one invite link makes OURS send join mail to any number of addresses (spoofed x-forwarded-for)"

   Smallest fix:

   - add a `join:invite:<id>` limit;
   - add an index on rate_events(created_at).
