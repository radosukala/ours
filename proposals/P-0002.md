# P-0002 — Show a person the time they spent in the feed, and do not keep it

**Status:** ADOPTED — by [`D-0005`](../decisions/D-0005.md) on 5 September 2026

## The problem

Every engagement-funded feed measures how long a person stays and hides the
number from them, because the number is the product. OURS Feed is not paid
by attention, so there is no reason to hide it — and there is a reason to
show it: a person deciding for themselves how long to stay needs the one
fact the incumbent keeps.

The v0 catalog in `FEED-PILOT.md` §6 has reminders and a session budget,
both of which interrupt. It has no plain, always-visible number that
informs without interrupting.

## Affected

The pilot cohort (a number on their screen); the implementers of Parts A
and C of `M-0003`. Nobody else: nothing leaves the device.

## Requested decision — `D-0005`, PRODUCT_MANDATE

Before Part A of `M-0003` runs, add to the v0 catalog in `FEED-PILOT.md` §6:

| Option | Layer | Default | Rule |
|---|---|---|---|
| time spent, visible: this session and today / this session / off | GOVERNED | session and today | R-TIME-SHOWN-NOT-KEPT |

and add to the rulebook articles Part A drafts (`envelopes/M-0003/A-records-and-kernel.md` §1):

| Article | Meaning | Class today |
|---|---|---|
| `R-TIME-SHOWN-NOT-KEPT` | the feed shows a person how long they have used it, in plain minutes, by default; it does not store, send, or use that number for anything else | `ENFORCED` by app test — no reading-duration value reaches the server · `CHECKED` for the display |

Design, for Part C:

- a small monospace line in the stream header — `4 min this session · 12
  min today` — measured by active viewing, using the same client-side
  timer Part C already builds for reminders;
- *today* is kept on the device only (local storage), resets at local
  midnight or when the person clears it, and is never synced or sent;
- the option's `why`, in the catalog: *We show you the number because we
  are not paid by it. We do not keep it because we should not have it.*

Provenance on the catalog record: `decision: D-0003` (the authority under
which the catalog is adopted), `mandate: M-0003`, `proposal: P-0002`,
`amended_by: D-0005` — so the settings page reads: *exists because P-0002 ·
decided D-0005 · built under M-0003*. The `proposal` and `amended_by`
fields are optional additions to `ours.option/v0.1`, accepted by the
provenance check when present.

## Alternatives considered

| Option | Counter-case |
|---|---|
| do nothing — reminders and a budget exist | both interrupt; a visible number informs without interrupting, and is the quieter default |
| make it `FLOOR` — always shown, no off | a stronger statement, but it overrides a person who finds the number oppressive; where a behavior can be personal it is; default-on is the honest maximum |
| keep it server-side for a weekly summary | rejected — the product would learn how long a person reads, which Part C already forbids and the proposed article forbids |
| wait until after the pilot | rejected — Part A has not run; adding the row now costs one decision; adding it later costs a catalog amendment and a receipt anyway, and the option would carry a patch's provenance instead of a proposal's |

## Cost and risk

Proposal: 0.2 hours, `ESTIMATED`. Decision: minutes. Build: inside Part C's
existing timer — under one hour of agent work, `ESTIMATED`. Risk: none to
any person; no data leaves the device.

## Unresolved — for the founder

1. Default value: *session and today* (recommended) or *session* only?
2. Placement: the stream header (recommended) or settings only?
3. Reset: local midnight (recommended) or a rolling 24 hours?
