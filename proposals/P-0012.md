# P-0012 — The build kit: instructions, rules and a check for coding agents

**Status:** ADOPTED, by the founder's words of 2 October 2026, as recorded
in [`D-0019`](../decisions/D-0019.md). D-0019 says which parts it reads as
an interpretation, and what is still open.
**Requests:** D-0019 (CONSTITUTIONAL)
**Proposed by:** the founder
**Drafted by:** an agent, from the founder's words and the records they
build on (D-0017, D-0018, THE-LAYER §3, §5 to §7.1)
**Evidence:**
[`P-0012.evidence-conversation-2026-10-02.md`](./P-0012.evidence-conversation-2026-10-02.md),
the founder's words, verbatim.

## The problem

M-0015 built the framework in readable words: the common agreement, the
projects, and "Build the next one". On 2 October the founder said that is
not enough to make building on our.one real.

- **Builders build with coding agents.** The founder doesn't expect anyone
  to build a project for our.one by hand, without AI.
- **So the agreement has to reach the agent.** Today it is a page a person
  reads. Nothing tells an agent what to build, what never to do, or how to
  check its own work.
- **The choice has to be obvious.** A builder should see two ways: build
  alone as before, and look for users, or build for the people who will use
  it, under the agreement.
- **It should feel like a system that is starting and running.** That
  needs tools, not only pages.

## What is proposed

1. **A build kit,** in the public repository under `kit/` and served by the
   site:
   - **`build.md`:** instructions a coding agent follows, step by step,
     served at `/build.md`. A builder gives the agent one line that points
     to it.
   - **`our-one.mjs`:** one file, with no dependencies and no network
     access. `init` sets a project up; `check` checks it against the rules;
     `rules` prints them.
   - **`our.one.json`:** the project's manifest. It says what the project is
     and who maintains it, where its source is and under which licence, where
     its costs are, and what it does with personal data: what it collects,
     why and for how long, which outside services receive what, which
     folders hold the code that touches it, and how a person exports and
     deletes it. It is a small form of THE-LAYER §5's service specification.
   - **The rules,** a block the agent keeps in the project's `AGENTS.md`.
2. **Rules, version 0,** drawn from the common agreement (D-0017 §B and §C,
   D-0018 §A) and THE-LAYER §6 to §7.1, each with how it is held. Ten
   machine checks, four things a person reads, and five safeguards that are
   our.one's to build.
3. **Enforcement in layers, each with its class:**
   - the agent's instructions (`DECLARED`);
   - a Claude Code stop hook that runs the check whenever the agent tries to
     finish (`CHECKED`; the builder can remove it);
   - a CI workflow (`CHECKED` as our.one sees it);
   - our.one's own run of the check on a proposed project, read by a person
     (`INTERPRETED`, with the `CHECKED` report);
   - the runtime safeguards, which are not built.
4. **What passing means.** A project that passes is ready to propose,
   nothing more. It isn't listed, approved or protected: technical admission
   is not a constituency (THE-LAYER §3).
5. **The feed carries the same manifest and passes the same check.** It is
   "the first project, with the same framework of ownership as other"
   (D-0017 §A).
6. **A page, `/build`, "Build on our.one":**
   - the two ways to build, side by side, with what holds each today;
   - the one line to give a coding agent;
   - what the agent does, the rules, and what the check can and can't tell;
   - then the proposal, by email as D-0018 decided.
7. **No registry, marketplace or listing.** D-0017 §H stands.

## What it does not do

- It builds none of the seven safeguards, and says so wherever it names
  them.
- It doesn't take proposals by any route but email.
- It doesn't decide whether projects that pass are listed (D-0017 §K.7).
- It doesn't deploy. M-0012 stays a draft until the founder's go, after its
  preconditions.

## Risks

- **A check can be read as approval.** Every place that shows the check says
  that passing makes a project ready to propose, nothing more.
- **Patterns can be evaded.** The import, package and phrase checks are
  `CHECKED`, not `ENFORCED`. What they can't see is listed for a person.
- **Rules stricter than the agreement's words.** Three of them go further
  than the agreement's text: no session recording, no data hubs, and a data
  boundary in code. They are the founder's to confirm (D-0019 §K).
- **The tool runs in other people's projects.** It must stay readable, make
  no network requests, print no secret it finds, and write only the files
  `init` names.
