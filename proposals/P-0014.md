## The problem

On 3 October the founder asked to publish our.one, and created the Vercel
project. Four things in the verified build stand between it and a true
first deploy:

1. **The hosting lines** on `/privacy` and `/power`, and the control record
   behind `/power`, say *"our.one is not deployed"*. So do `/privacy`'s and
   the house rules' lines on the administrator. On the deployed site they
   would be false. M-0012 already names this as precondition 11 (D-0020
   §G).
2. **The founder's administrator account can't be made.** The founder
   script accepts only fictional `example.test` addresses, by M-0010's rule,
   which says a later release mandate changes it. M-0012's scope doesn't
   include the script. Without the account, nobody can sign in or open
   seats.
3. **The migrations have no safe place to run.** M-0012 says the agent runs
   them and creates the account, and also that no agent handles a secret.
   The database's address is a secret, and it lives only in Vercel.
4. **The weekly email would never run.** Vercel's scheduler calls a route
   with GET; the weekly email's route answers only POST, and no schedule
   exists.

Two more things came up:

- **Where the functions run.** Vercel runs a project's functions in one
  region, and a new project's default is in the United States. M-0012 puts
  the database in an EU region. Left as it is, every page would cross the
  Atlantic, and people's data would be processed there.
- **The repository.** The founder asked whether to start a new repository
  holding only the latest version.

## What is proposed

1. **Keep `ours`,** with its history. Commit from now on with the founder's
   GitHub no-reply address. Give the README a section for visitors who
   arrive from our.one.
2. **The site says where it runs.** Every sentence about hosting, the
   database, the administrator and deployment says what is true on the
   server that renders it: on Vercel's production deployment, what runs it,
   read from the platform and from the database address's host, which is
   never shown; anywhere else, that the copy isn't the deployed site.
3. **A release Vercel runs.** The production build applies the migrations,
   and creates the founder's account from three settings the founder enters
   in Vercel, if no account exists yet. Previews and local runs never touch
   the database. Nothing is printed but what was done.
4. **The weekly email on Vercel's schedule:** GET as well as POST, with the
   same secret, on Mondays at 08:00 UTC.
5. **Frankfurt:** the functions run in `fra1`, beside the database.

## Alternatives considered

| | Option | Why not |
|---|---|---|
| R1 | A new repository with only the latest version | 28 files in the records and receipts cite 63 of this repository's commits, among them the commits that show each verifier's tests committed before the fixes. A new repository breaks all of them. It also hides nothing: this one is already public, and stays public unless deleted. |
| R2 | Rewrite the history, to change the author's address | Every commit's hash changes, so the same 63 citations break. The address is already public. |
| H1 | Write the hosting lines into the record at the release | The release would deploy a build different from the verified one (AGENTS.md §5). |
| H2 | The founder types the hosting facts into settings | A typed setting can be wrong; what the platform and the database address report can't be. The data controller's name stays a setting, because nothing can detect it. |
| M1 | The founder runs the migrations and the founder script from a terminal | It works, once, but the founder handles the database's address by hand, and every later migration needs the same. |
| M2 | Create the founder's account at the first sign-in, from a setting | New code on the sign-in path, the most sensitive in the application. The founder script's rule (the first account only, under a lock) is already tested. |

## What the review of the history found

Checked by the agent on 3 October 2026, with `git` over every commit:

- **131 commits** on one branch, from 30 August to 3 October 2026, about
  15 MB, mostly receipt screenshots;
- **no key, token, private key or database password** in any line ever
  added: the matches are fictional test values, AWS's published example
  key and placeholder addresses;
- **`docs-internal/` never committed,** and no `.env` file but the blank
  templates;
- **no other person's contact data:** the only real address in any file is
  `privacy@ctrlai.com`, and the reviewers quoted in the evidence are not
  named;
- **nothing ever deleted** from the tree, so the history holds today's files
  and their earlier versions;
- **the founder's personal address** as the author of every commit;
- **one line about Ctrl AI, Inc. that was wrong:** its registered office,
  added and removed on 30 August (commit `fcec996`). It is still in the
  history.

## Cost and risk

About half a day of agent work, `ESTIMATED`, and one verification round.
The risk is the release step: a build that writes to the production
database. It runs only in Vercel's production build, takes the same lock
as the founder script, and prints nothing that identifies anyone.
