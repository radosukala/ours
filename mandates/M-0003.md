## The first product mandate

M-0001 built a page that explains why it is running. M-0003 builds a product
that explains why every option in it exists. Same discipline, new surface:

```bash
pnpm ours check M-0003
```

If that refuses, no part of the work starts. When the work is done, the
working tree is checked against this mandate's scope:

```bash
pnpm ours check M-0003 --changed
```

## Objective

Build OURS Feed v0 in `apps/feed` — profiles, posts and replies, follows, a
chronological home stream, export and deletion — together with the feed
Cell's rulebook, option catalog, and ranking contract as repository records;
a settings page rendered from that catalog in which every option shows the
rule, decision, and mandate that created it; endorsement of defaults recorded
as demand; a steward moderation path with public receipts; and the kernel
check that refuses a build whose options lack provenance.

## Human outcome

A person in the pilot cohort can use a feed that looks like the ones they
know, open its settings, read why every option exists and who decided its
default, change what is theirs to change, endorse a different default for
everyone, ask any feed item why it appeared, and leave with their data —
while every surface states that a founder, not members, set the defaults.

## Adopted constraints

**Projection, not story**

- The rulebook, catalog, and ranking contract are repository records read at
  build time. The interface renders no option that has no record, and a test
  fails if a catalog option is not rendered.
- Every GOVERNED default names the decision that set it and is labelled, in
  body type, as set by founder bootstrap and not yet voted.
- Endorsements and proposals are recorded demand. No interface element
  renders them where a vote result would be.

**The contract is structural**

- The ranking input type excludes dwell time, predicted engagement, reaction
  counts, paid boosts, advertiser interest, and inferred sensitive
  attributes.

**Privacy and independence**

- No analytics, tracking, third-party script, remote font, advertising, or
  social login. Sign-in is by emailed link through a replaceable provider.
- Adults only, self-attested at sign-up. No feature designed for minors.
- No points, ordinals, badges, ranks, or scarce or transferable artifacts.
- Export and deletion exist before any other feature is considered done.

**Bootstrap truth**

- Nothing is deployed, no environment is named, no domain is touched.
- No fact marked `[CONFIRM]` is resolved, and no data controller is named.

## Hypotheses

1. A settings page that explains itself is understood by a non-technical
   person without coaching.
2. Endorsement counts on defaults are used, not merely praised.
3. The option catalog survives the interface without a schema change.
4. A person alone on the feed finds the profile, the settings, and the
   export worth having.

```text

envelopes/**   apps/proof/**     packages/verifier/**   exit/**   vercel.json
```

The product renders records from `rules/feed/`, which it may write, and
cites `D-0003` and this mandate, which it may not. An implementer who found a
default inconvenient could otherwise change the decision that set it. The
envelopes are the mandate's own instructions to its agents and are denied
for the same reason a mandate cannot rewrite itself.

## Acceptance tests

1. `pnpm ours check M-0003` authorises before the build begins, and
   `pnpm ours check M-0003 --changed` authorises the finished working tree.
2. The option catalog validates, and at least three invalid catalogs refuse
   for the correct reason — a missing rule, an unauthorised decision, an
   overridable `FLOOR` option.
3. Every rendered option resolves to a catalog record and every catalog
   record is rendered; the test runs in both directions.
4. Every `GOVERNED` default displays its decision and the founder-bootstrap
   label in body type.
5. Every feed item's explanation is generated by the ranking function that
   ordered it.
6. The ranking input type contains no prohibited signal, and a test fails the
   build if one is added.
7. Endorsements and proposals record and display counts under the demand
   label and nowhere else.
8. A report produces a steward action with a public receipt whose private
   details are redacted.
9. Export returns the person's data with the rulebook, catalog, and contract;
   deletion removes personal data and states its residue.
10. The interface makes no request to a third-party origin.
11. The kernel's prohibited-claim scan over every copy file in `apps/feed`
    finds nothing.
12. Legible in light and dark at 375 px and desktop; every control keyboard
    reachable with visible focus.
13. `pnpm typecheck` and `pnpm test` pass.

## Evidence required

- a conformance report mapping every rulebook article to a check and its
  class;
- build receipts per part recording agent, model, scope touched, dependencies
  added with reasons, and failures;
- narrow-mobile and desktop inspection;
- a proposed `M-0003-RELEASE`, written in the final receipt for founder
  review — the agent proposes the release mandate; it does not file it.

## Stop conditions

- an option would have to be rendered without a catalog record;
- a default would have to be chosen by the implementer rather than by
  `D-0003` or the adopted catalog;
- an acceptance test would require weakening a constitutional article or a
  rulebook article;
- a required fact is marked `[CONFIRM]` or would name a data controller;
- a feature would require a third-party origin at runtime;
- the work requires a path outside the allowed scope.

## Risk

`LOW` and `ADDITIVE` **at build time**: a new application, new records, and
new checks, none deployed, no person affected. The risk changes entirely at
release — personal data, a moderation duty, a controller — and
`M-0003-RELEASE` must carry that honestly rather than inherit this
classification.

## Rollback

Remove `apps/feed` and `rules/feed`; revert the schema, kernel, CLI, and
workspace changes. No record above this mandate is modified, and nothing is
deployed.

**Irreversible residue: none** at build time. At release this changes, and
`M-0003-RELEASE` carries it: once people have signed up, personal data
exists and posts have been read.
