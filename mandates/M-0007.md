## What this mandate is for

`M-0006` built the gate. This builds the ground the gate admits to, on
invented data: a runtime that holds a community's records, hands an
application a capability scoped to its contract, checks every disclosure
at the boundary, logs every reach, and lets the application be replaced
while everything the community owns stays where it is. The fictional
workshop's booking tool is the tenant; its replacement is the test.

```bash
pnpm ours check M-0007
pnpm ours check M-0007 --changed
```

## Objective

Build, in `layer/`, the v0 runtime: identity by emailed sign-in link; the
standing register with a public count; one database in which every row is
scoped to a person and a community; the layer client implemented as a
server-side API that hands each application a capability scoped to its
contract's reads and writes; the disclosure API, checking every payload
field by field against the permitted disclosures and refusing any origin
the contract does not name, with an outbound allowlist so that nothing
else leaves; an access log naming the permitting article for every read,
write, and disclosure; export as a bundle the offline verifier accepts;
deletion with its residue stated; and each tenant's own trace, bundle, and
served digest. Build, in `apps/dilna-fixture/`, the booking tool to the
pinned specification 0.1 through a spec-driven pipeline of the operator's
choice, reaching the layer only through the client, with the
specification's seven named tests made executable. Build a second
implementation, `apps/dilna-fixture-2/`, and rehearse the swap: it passes
the gate against the same pinned specification, the transition
requirements are checked, a member's export before and after verify and
match, and the receipt records what broke. Fictional data only; nothing
deployed.

## Human outcome

A reader watching the fixture can see a tool admitted, used, replaced, and
the community's records — members, bookings, decisions — unmoved through
the replacement; can see an application refused at the boundary when it
reaches for what it was not granted; and can see, on every surface, that
nobody in it exists.

## Adopted constraints

**The boundary is the runtime's, not the application's**

- An application has no database, file system, or sockets of its own; it
  runs against the client API with a capability the runtime issues from
  the pinned contract, and a test fails the build if it reaches anything
  else.
- The disclosure API refuses an undeclared origin and an undeclared field
  to a declared origin, and logs every permitted disclosure with its
  fields and article; the tests hold both refusals and the log.
- The static check of `M-0006` runs at admission and the runtime holds the
  same contract at execution; a difference between the two is a failure,
  not a feature.

**The rules are read, never written**

- `communities/**` and `spec/**` are denied. The implementer reads the pin.
  If the specification is wrong, the work stops and the receipt says so;
  an amendment is the fixture's decision, re-pinned.

**The swap is rehearsed, not described**

- The second implementation is admitted by the same gate against the same
  pin; the transition requirements of the specification are checked record
  by record; a member's export before and after verify offline and match;
  what did not carry across is in the receipt, not hidden.

**Bootstrap truth**

- Every person, booking, and vote is the fixture's, invented and labelled
  `FICTIONAL` on every surface the runtime renders. No real person signs
  in. No environment is named, no domain touched, no name registered.
- No fact marked `[CONFIRM]` is resolved. No controller or holder is named.
- No analytics, tracking, third-party script, remote font, or advertising.

## Hypotheses

1. A runtime capability plus an egress allowlist can be held on ordinary
   hosting without a custom sandbox.
2. A second implementation can replace the first with the records intact
   within one working day of agent time.
3. The seven named tests of the specification can be made executable
   without changing the specification.
4. A member's export from the layer verifies with the unmodified offline
   verifier.

## Acceptance tests

1. `pnpm ours check M-0007` reports *authorised for execution* — every
   record in the chain and every prerequisite decision adopted.
2. The runtime capability refuses a read outside the contract and a write
   to an undeclared class; both tested at runtime, not asserted.
3. The disclosure API refuses an undeclared origin, and refuses an
   undeclared field to a declared origin; both tested at runtime.
4. Every read, write, and disclosure appears in the access log with its
   permitting article.
5. The seven `T-` tests of the specification pass against the tenant.
6. The second implementation passes the gate; every record carries across
   with its meaning per the transition requirements; a member's export
   before and after verify offline and match.
7. Each tenant serves its trace, its bundle, and a digest equal to the
   verified build.
8. No request to a third-party origin; the prohibited-claim scan over every
   copy file finds nothing; the fixture label is on every surface.
9. `pnpm typecheck` and `pnpm test` pass; `pnpm ours check M-0007 --changed`
   authorises the finished working tree.

## Stop conditions

- any prerequisite does not hold;
- confinement would require infrastructure the founder has not chosen;
- a `T-` test cannot be made executable without changing the
  specification;
- the swap loses a record's meaning;
- any real person's data would be needed;
- a required fact is marked `[CONFIRM]`;
- the work requires a path outside the allowed scope.

## Risk

`LOW` and `ADDITIVE` at build time: a runtime holding invented data, two
applications, nothing deployed, no person affected. At release the risk
changes entirely, and the release mandate carries it.

## Rollback

Remove `layer/` and the two applications; revert the package and workspace
changes. **Irreversible residue: none.** Nothing real was held.
