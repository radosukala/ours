## The decision

### A. One repository, with its history

- **`ours` stays the one public repository** for the code, the kit and the
  records, with its whole history. No new repository, and no history
  rewritten.
- **From now on, commits carry the founder's GitHub no-reply address.** The
  earlier commits keep the address they have, because rewriting them would
  change every hash the records cite (P-0014).
- **The README gets a first section for visitors who come from our.one:**
  what our.one is, where the site's code, the kit and the records are, and
  why the history is kept.
- *Interpretation:* the founder asked whether to start a new repository
  with only the latest version. The agent recommended against it, and the
  founder then created the Vercel project from `ours`.

### B. The name stays our.one

- **D-0012 §C stands:** our.one is the public name and address, and OURS
  the working name of this repository and its records.
- **ONE moves to `oneburger.cz`** before `our.one` points at the new site,
  as M-0012 says.
- *Interpretation:* the founder asked whether to use `oursnow.co` or
  `ourstoday.com` with the brand OURS instead. The agent recommended
  our.one: both earlier names state ownership in the present tense, which
  D-0012 forbids, and both still serve earlier sites. The founder answered
  *"ok lets publish it to our.one"*.

### C. The site says where it runs

M-0012's precondition 11, decided:

- **Every sentence about hosting, the database, the administrator or
  deployment says what is true on the server that renders it.**
- **On Vercel's production deployment,** as the platform's own settings
  report it:
  - Vercel runs the site, in the region the platform reports;
  - the database is named from its address's host, with its region; the
    address itself is never shown;
  - email is as it is today, from the same test that sends it;
  - each of these is shown as stated in this server's configuration.
- **Anywhere else,** in development, in a preview or in a test, the page
  says that this copy isn't the deployed site.
- **The administrator lines say what the database holds:** no administrator
  yet, or the founder's account as the only one.
- **`/privacy` names Vercel and Neon among those who receive data,** with
  what each receives, when the server runs on them.

### D. A release Vercel runs

- **The release runs only when the founder names it.** It runs in Vercel's
  production build of the one commit the founder names in `OURS_RELEASE`,
  a setting the founder enters in Vercel with the go M-0012 requires. A
  push alone touches no database: BUILD never becomes DEPLOY by itself
  (`AGENTS.md` §8).
- **What our.one serves changes only when the founder promotes a
  deployment.** The founder turns off Vercel's automatic assignment of the
  domain to new production builds; a build waits, staged, until promoted.
- **That build applies the migrations.**
- **It creates the founder's administrator account** from three settings
  the founder enters in Vercel: an email address, a handle and a name.
  It does so only if no account exists yet, under the founder script's
  rule: the first account only, with the check and the insert in one
  locked transaction.
- **Nothing else touches the database:** other commits' builds, preview
  builds and local runs don't.
- **The build log says only what was done.** It never prints an address, a
  sign-in link, a key or the database's address.
- **The founder then signs in at `/signin`,** by email.
- **The founder script stays as M-0010 left it:** fictional addresses only.
- **The functions run in Frankfurt (`fra1`),** beside the database. A new
  Vercel project's functions run in Washington, D.C. unless a region is
  set.

### E. The weekly email runs on Vercel's schedule

- **Vercel's scheduler calls the route with GET,** sending `CRON_SECRET` as
  a bearer token. The route answers GET exactly as it answers POST, and
  refuses both without the secret.
- **The schedule is Mondays at 08:00 UTC.** On Vercel's free plan, the call
  can come at any point in that hour. Without `CRON_SECRET`, the weekly
  email stays switched off.
- *Interpretation:* the day and hour are the agent's choice. The founder
  can change them.

### F. Where the keys live

- **The real keys live only in Vercel** (M-0012). `apps/web/.env.local` holds

- **The founder moves the real keys out of `apps/web/.env.local`.**
- **Until the founder says the file is clean,** no agent opens it or runs
  anything that reads it. Every agent run happens in a clean worktree,
  which doesn't have the file.

## Prohibited under this decision

- a new repository for this work, or a rewritten history;
- a page that says our.one is deployed, or names a host, a database or an
  administrator, unless the server rendering it runs there or holds it;
- printing an address, a sign-in link, a key or the database's address in a
  build log;
- touching the database from anywhere but Vercel's production build of
  the commit the founder names;
- an agent opening a file that holds a real key, or entering one;
- deploying under `M-0018`.

## Reasons

1. **The history is the evidence.** 28 files in the records and receipts
   cite 63 of the repository's commits, among them the commits that show
   each verifier's tests committed before the fixes. A fresh repository
   would hide nothing that isn't already public, and would break them all.
2. **A sentence about the running site should come from the running site.**
   The platform and the database's address can't be wrong about where the
   server runs. A sentence written at the release would make the deployed
   build differ from the verified one.
3. **No agent holds the database's address.** The release runs where the
   address already is, in Vercel's production build.
4. **A push is BUILD; a release is DEPLOY.** Naming the commit, and
   promoting it, keeps the second in the founder's hands. Without them,
   every push to `main` would migrate the real database.
