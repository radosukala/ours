# D-0019 — The build kit: instructions, rules and a check for coding agents

**Status:** ADOPTED by the founder under bootstrap authority on 2 October
2026. The founder's words, in full in
[`P-0012.evidence-conversation-2026-10-02.md`](../proposals/P-0012.evidence-conversation-2026-10-02.md):

> We should have clear instruction, and enforcment for rules and guide for
> coding agents for how to build project to be able to aspire be part of
> our.one ... It should be obvious and we should have tools for that.

**How this record was made.** An agent drafted it from those words and from
the records they build on. Where it interprets them, it says so (§B, §C,
§K). The founder's review of the exact wording, and of the rules in §C, is
**PENDING**, and an amendment is a new record.

**Class:** CONSTITUTIONAL. It sets the rules every project proposed to
our.one is checked against, and it amends D-0018 §C and the draft M-0012.
**Authority:** founder bootstrap
**Prerequisites:** `D-0017`, `D-0018`
**Machine projection:** [`D-0019.yaml`](./D-0019.yaml)

## The decision

### A. The founder's requirement

**Adopted, as the founder's requirement:**

- builders build with coding agents, so our.one gives the agent what it
  needs: instructions it can follow, rules, enforcement of the rules, and
  tools;
- the choice between building alone, as before, and building for the people
  who will use it, under the common agreement, is shown side by side.

### B. The build kit

**This record reads "tools" as a kit in the public repository, under
`kit/`, served by the site from the deployed commit:**

- **`build.md`,** served at `/build.md`: instructions a coding agent
  follows, step by step. A builder gives the agent one line that points to
  it.
- **`our-one.mjs`,** served at `/kit/our-one.mjs`: one file, with no
  dependencies and no network access.
  - `init` creates what a project is missing.
  - `check` checks the project against §C.
  - `rules` prints the rules block.

  `build.md` carries the tool's SHA-256, so an agent can confirm it has the
  published file.
- **`our.one.json`,** each project's manifest, with a schema served at
  `/kit/our.one.schema.json`. It says:
  - what the project is, who maintains it, where its source is, and its
    licence;
  - where its costs are;
  - what it does with personal data:
    - what it collects, why and for how long;
    - which outside services receive what;
    - which folders hold the code that touches it;
    - how a person exports and deletes it.

  It is a small form of THE-LAYER §5's service specification.
- **The rules block,** which `init` writes into the project's `AGENTS.md`
  and `check` compares, word for word.

### C. The rules, version 0

**The rules are the common agreement's, put in terms an agent can act on.**
Three of them go further than the agreement's words, and are marked (*).
Each says how it is held.

| # | Rule | Held by |
|---|---|---|
| 1 | **Keep personal data inside the boundary.** Only code in the folders the manifest names may use a database or a file store. (*) | `CHECKED` for JavaScript and TypeScript, by imports |
| 2 | **Declare before you collect:** what, why, and for how long. | `STRUCTURAL` in the manifest · `INTERPRETED`: is it all of it? |
| 3 | **Name every service that receives data:** who, what and why. | `CHECKED` for the services the tool knows, by package |
| 4 | **No ads and no tracking:** no ad networks or pixels, no Google Analytics or Tag Manager, no session recording (*), no data brokers or data hubs (*). | `CHECKED` for the packages and script addresses the tool knows |
| 5 | **Nothing is sold:** neither people's data nor the project. | `INTERPRETED` · the agreement, once signed |
| 6 | **People can leave:** export and deletion keep working. | `STRUCTURAL`: described · `INTERPRETED`: does it work? |
| 7 | **Costs are public,** in a file the manifest names. | `CHECKED`: the file exists and is filled in |
| 8 | **No secrets in the code.** | `CHECKED` for the patterns the tool knows |
| 9 | **Say only what is true.** Until our.one's records say otherwise, a project is its maintainer's. It isn't presented as its users' property, or as approved, listed or protected by our.one. | `CHECKED` for the phrases the tool knows |
| 10 | **Run the check before finishing,** and never change the check or the rules block to make it pass. | `CHECKED`: the block is present and unchanged · `DECLARED`: the rest |

**Two structural checks come with them:**

- **The manifest** is complete (`STRUCTURAL`).
- **The code is under an open-source licence,** in a licence file, named in
  the manifest (`CHECKED`).
  - This follows D-0017 §B's continuity: a successor needs the code
    licence.
  - It also follows §C: builders grant the rights a successor needs.

**Not built, and listed by every run of the check:**

- **What our.one must build for a protected service.** These are D-0018
  §A's safeguards: no keys, reach and leave at runtime, the record, and
  custody.
- **What a person must read when a project is proposed.** Is the declared
  data all of it? Do export and deletion work? Is nothing sold? Does the
  proposal say what D-0017 §G asks?

**A change to the rules is a new rules version, by a new decision.** The
block carries its version, and the tool checks against its own.

### D. Enforcement, in layers

| Layer | What it does | Class |
|---|---|---|
| The rules block in `AGENTS.md` | Tells every agent working on the code | `DECLARED` |
| A Claude Code stop hook, written by `init` | Runs the check whenever the agent tries to finish. If a rule fails, it sends the agent back once, then tells the person | `CHECKED`: the builder can remove it |
| A CI workflow, written by `init` | Fails the build when a rule fails | `CHECKED` as our.one sees it. `ENFORCED` in the builder's repository only if they require it |
| our.one, when a project is proposed | Runs its own copy of the check on the commit named, and a person reads the result and the open items | `INTERPRETED`, with a `CHECKED` report |
| The runtime safeguards (D-0018 §A) | Hold the line while a service runs | Not built |

### E. What passing means

**A project that passes the check is ready to propose. Nothing more.**

- It is not listed, approved or protected.
- Technical admission is not a constituency (THE-LAYER §3). The people who
  would use the service decide.
- A project becomes a protected service only by a decision on our.one's
  records, once the holder exists (D-0017 §D, §E).
- **No registry, marketplace or listing is built.** D-0017 §H stands.

## Prohibited under this decision

- **Describing a passing check** as approval, listing, certification or
  protection.
- **Describing any safeguard as built** before it is.
- **A tool that makes network requests,** writes outside the files `init`
  names, or prints a secret it finds.
- **Changing the rules without a new rules version** and a decision.
- **Collecting proposals by any route but email.**

## Reasons

1. **The agreement only binds what the agent reads.** If builders build
   with agents, the rules have to be in the agent's instructions and in a
   check it runs itself, not only on a page.
2. **Each layer says what holds it.** A rule in `AGENTS.md` is a request; a
   hook can be removed; our.one's own run on the proposed commit is the
   check that counts. Saying so keeps the system honest while it grows
   (AGENTS.md §7).
3. **THE-LAYER §5 and §6 asked for this shape:** a specification the
   project carries, and a gate that compares the code with it. This is the
   smallest version that works on someone else's project.
4. **The tension with AGENTS.md §12.** That rule warns against generalized
   machinery before one real loop needs it. The kit is instructions and one
   checker: no registry, no accounts, no marketplace. It is what the
   builders' invitation (D-0017 §A) needs, now that the founder has said
   builders arrive with agents.
